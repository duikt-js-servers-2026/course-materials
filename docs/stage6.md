## 1. Як вмикається автентифікація

`createRestApp` з етапу 5 отримує нову необов’язкову опцію `auth`:

```js
createRestApp({
  dbFile: 'data/app.db',
  auth: {
    secret: process.env.JWT_SECRET,  // секрет для підпису токенів, щонайменше 16 символів
    tokenTtl: 3600,                  // термін дії токена в секундах (за замовчуванням 3600)
    adminEmails: ['admin@example.com'], // хто при реєстрації отримує роль admin (необов’язково, за замовчуванням [])
  },
});
```

- Якщо `auth` **не передано** - API працює, як на етапі 5 (так його запускають тести етапу 5).
- Якщо передано - з’являються маршрути `/api/auth/...` і захист маршрутів.
- Під час запуску з консолі беріть налаштування зі змінних середовища (`JWT_SECRET`, `TOKEN_TTL`, `ADMIN_EMAILS`). **Секрет ніколи не комітьте в репозиторій.**

## 2. Користувачі

Таблиця `users`: `id`, `email` (унікальний), хеш пароля, `role` (`user` або `admin`).

**Паролі зберігаються лише у вигляді хешу.** Використайте вбудований `crypto.scrypt` / `crypto.scryptSync` із випадковою «сіллю» для кожного користувача, або пакет `bcrypt` / `bcryptjs`. Тести перевіряють, що пароля у відкритому вигляді немає у файлі бази даних.

## 3. Маршрути автентифікації

| Запит | Успіх | Помилки |
|---|---|---|
| `POST /api/auth/register` `{ email, password }` | `201` `{ id, email, role }` - **без** пароля й хешу | `400` (некоректний email, пароль коротший за 8 символів; `details` по полях), `409` email уже зареєстровано |
| `POST /api/auth/login` `{ email, password }` | `200` `{ token }` | `401` - однаково для неіснуючого email і неправильного пароля |
| `GET /api/auth/me` з заголовком `Authorization: Bearer <token>` | `200` `{ id, email, role }` | `401` |

Роль `admin` отримує користувач, чий email є в `adminEmails`; усі інші - `user`.

## 4. Токен JWT

- Формат - стандартний JWT із трьох частин, підпис **HS256** вашим `secret`.
- У payload обов’язково: `sub` - id користувача, `role`, `exp` - час закінчення дії (секунди з 1970 р.), бажано й `iat`.
- Можна користуватися пакетом `jsonwebtoken` або реалізувати HS256 самостійно через `crypto.createHmac` - на захисті поясните, як працює підпис.

Токен **не приймається** (`401`), якщо:
- немає заголовка `Authorization: Bearer ...`;
- підпис не збігається (наприклад, хтось змінив у payload `role` на `admin`);
- минув термін дії (`exp`);
- користувача з таким `sub` уже немає.

## 5. Хто що може

| Дія | Хто |
|---|---|
| усі `GET` (категорії, товари) | будь-хто, без токена |
| `POST`, `PUT`, `PATCH`, `DELETE` товарів | будь-який автентифікований користувач |
| `POST`, `PATCH`, `DELETE` категорій | лише `admin` |

Коди: немає токена або він недійсний - `401`; токен дійсний, але роль недостатня - `403`. Усі помилки - JSON `{ "error": "..." }` через вашу централізовану обробку помилок.

Перевірку токена й ролі зробіть **middleware** (наприклад, `requireAuth` і `requireAdmin`), а не повторюйте код у кожному маршруті.

## Перевірка

```bash
npm test
```

Тести етапу - у `test/stage6.test.js` (не змінюйте їх). Вони перевіряють реєстрацію, вхід, вміст токена, хешування паролів, доступ за ролями, підроблений токен і закінчення терміну дії. Етап готовий, коли проходять усі тести - етапів 1-6.

Перевірте й руками через curl або Postman:

```bash
JWT_SECRET=dev-secret-change-me-123 ADMIN_EMAILS=you@example.com node src/rest.js
curl -i -X POST localhost:3000/api/auth/register -H 'content-type: application/json' -d '{"email":"you@example.com","password":"password123"}'
curl -i -X POST localhost:3000/api/auth/login -H 'content-type: application/json' -d '{"email":"you@example.com","password":"password123"}'
curl -i localhost:3000/api/auth/me -H 'authorization: Bearer <токен>'
```

На заліку ви показуєте весь проєкт: від `calc` до захищеного API.
